# 0014: The admin approves what needs approval, and there is no delegate approver

- **Date:** 2026-11-10
- **Class:** major
- **Issue:** none; the admin decided in chat on 2026-11-10 ("Yes, simplify")
- **Status:** accepted
- **Supersedes:** [0012](0012-gardener-delegate.md)

## Context

Decision 0012 added a delegate account that could approve and decide within a grant, so work kept moving when the admin was away. The admin chose to simplify instead: fewer changes need an approval, and no second approver exists. Branch freshness ([0013](0013-branch-freshness-by-overlap.md)) is part of the same simplification, since it lets PRs land in parallel.

## Decision

- **No delegate.** `delegates` and `tiers.adminOnlyPaths` are removed from `pipeline.config.json`. dev-pipeline's delegate code stays in the tree and does nothing without that key, so the gate behaves as it did before 0012. Only the admin's approve, decide and rearm commands count. The decision commands are unchanged. `models` stays.
- **A shorter list of what needs the admin.** `tiers.t2Paths` goes from 44 entries to 36, and the 15 it moves to T1 are those that only needed a person because everything did. Every other change merges at T1 once CI, the council and the gate pass. What stays T2:
  - pipeline and permission files: `.github/**`, `.pipeline/**`, `pipeline.config.json`, `pipeline.lock.json`, `.claude/settings*.json`, `.claude/hooks/**`;
  - the review machinery: `.claude/agents/**`, `.claude/workflows/**`, every skill in `.claude/skills/**` (agent instructions, and `babysit-pr/scripts/pr-wait` runs with the admin's `gh` login), `REVIEW.md`, `**/CLAUDE.md`, `**/AGENTS.md`;
  - the rule and licence files: `docs/POLICY.md`, `docs/PRD.md`, `LICENSE*`, `THIRD_PARTY*`, `TRADEMARKS.md`, `SECURITY.md`, `build/check-policy*`, `crates/deny.toml`, `build/origins.json`, `build/airgap.mjs`, `sidecar/installer/licences.json`, `build/packs-sources.json`, `build/csm/NOTICES.txt`, any `NOTICE` file under `sidecar/installer`, the licence files in `crates/vendor/**`, and `docs/decisions/**`;
  - four things kept for security, named so the admin can strike any of them: `sidecar/**` (the networked native helper), `**/build.rs` and `.cargo/**` (code that runs at build time), `crates/vendor/**` (vendored third-party code) and `build/release/**` (what gets published).
- **Moved to T1:** `.gitattributes`, `**/auth/**`, `**/billing/**`, `**/migrations/**`, `build/build.mjs`, `build/gates.mjs`, `build/rust.mjs`, `build/e2e.mjs`, `build/eval-allowlist.json`, `build/check-quarantine.mjs`, `build/verify-scope.mjs`, `crates/rust-toolchain.toml`, `**/package-lock.json`, `**/Cargo.lock` (outside `sidecar/`, which stays T2), and `.node-version`. A change to `package.json` scripts still needs the admin.
- **Bigger PRs.** The admin's direction on 2026-11-10 was to "reduce the number of PRs, and make the work done by each much larger", to lengthen the time between PRs and the work done without a person. `.pipeline/AUTONOMY.md` now says to batch related work: one PR may close several issues from the same area, one commit per issue, each fix kept narrow. The `autopilot` skill fills a branch with related `ready` issues before filing. A T2 path never goes into a T1 batch: it is split out into its own PR, so the admin still approves each T2 change alone. Both files now differ from dev-pipeline's, so the next `pipeline update` keeps them for a hand merge.
- **A two-phase council.** The admin's direction on 2026-11-10 was to experiment with ever larger PR scope, but with looping council rounds for each, "where the sonnet model is used for all council chairs until all issues are resolved or only low issues remain after at least two subsequent rounds", then, on the final round, to switch every chair to Opus for an extra level of quality review, with the same rule for close-out. In `.pipeline/lib/ledger.mjs`, `.pipeline/council.mjs` and `.claude/workflows/council-round.js`:
  - **Loop phase:** every seat and the verifier run on `council.loopModel` (Sonnet), whatever their agent files say. Rounds repeat until no blocker or should is open and the last two rounds in a row raised nothing above a nit.
  - **Close-out:** the same rule on `council.closeModel` (Opus), so at least two Opus rounds. A blocker or should found there is fixed, and close-out carries on on Opus.
  - **"Two in a row"** means two clean rounds on the same content: a change to the code starts the count again, and a repeat of a finding the author already answered doesn't count as raising it, while a fixed bug that comes back does, as a new finding to answer, and so does a more severe finding than the one already answered at that place. The caps count every round in a phase, clean or not, and a docs-only change gets the loop cap too.
  - **The verdict** is rendered only after close-out converges. The ledger records each round's phase and model, and the verdict records the rounds and model of each phase.
  - **Replaced:** `maxRounds`, `maxRoundsSensitive`, `t1Model`, the confirmation round and step-back. Hard caps per phase, `council.maxLoopRounds` (16) and `council.maxCloseRounds` (8) per PR, park a change that doesn't converge, with a summary left on the PR for the admin. The admin confirmed a cap in chat on 2026-11-10 ("Keep the cap"), and then doubled the standing caps from 8 and 4 the same day ("Double the standing council round caps for both sonnet and opus"). `maxDiffGrowth` stays and is measured from the first round's diff.
  - A docs-only change (T0) still gets one round.
  - **A one-off grant, per PR.** While this PR was in close-out under the old cap of 4, the admin granted it 2 more Opus rounds on 2026-11-10 ("approve One-off: allow 2 more Opus rounds for this PR only"), and 2 more again the same day, when a merge of main added the `gw-hydro` crate and the freshness test needed its group. Its findings were real bugs fixed one at a time, so it was settling, and parking it would have held up the changes behind it. The admin then doubled the standing caps, so this PR's grant went back to 0 and its cap is the standing 8. The mechanism stays: `extraRounds.<phase>` in a PR's own ledger, a whole number that `capFor` adds to the config cap, so a grant never reaches the config or another PR. A grant like this is the admin's to give, in their own words, per PR.
  - `council.maxSeats` is 6, the code's default, so the cap no longer drops `council-geo-correctness` from a change that touches geodesy (issue #168). The security and architect seats still never drop on T2.
  - These files differ from dev-pipeline's, so the next `pipeline update` keeps them for a hand merge, and the rule is a candidate to go upstream.
- **The baseline** carries over from 0012: from 2026-11-07 to 2026-11-09, 62 merges (T0 4, T1 30, T2 27, 1 revert), 39 admin approvals, approval wait from PR opening a median of 0.98 hours and a p90 of 7.6 hours, and a decision wait with a median of 1 hour. Reviewing a week of the new setup against it is how to tell whether this helped.

## Consequences

- Fewer approvals: the 15 moved paths merge without the admin.
- Review costs more: at least four rounds for a change with code in it (two on Sonnet, two on Opus), up to twenty-four before it parks. A parked change waits for the admin. The caps count every round in a phase, so if close-out has used its rounds and a later update changes the change hash (a merge that rewrites the PR's own lines), there is no round left to review it, and the PR parks for the admin.
- A verdict's `rounds` now counts both phases, so the digest's "PRs at 5+ rounds" figure reads higher than the baseline's and is not comparable with it until the digest reads `phases`.
- `docs/decisions/**` stays T2, so a decision record always needs the admin's approve, even one that cites a decide. Dropping that entry would let a cited record merge as T0 through `tiers.decisionPaths`.
- `.gitattributes` moved to T1, so the council reads attributes from the merge base (`git --attr-source=<merge base> diff --no-ext-diff --no-textconv`, in the seats' brief and in the size count). A `-diff` or `binary` line added by the change can't blank what the seats read. The base's own binary rules still apply, so the seats' brief tells them to re-read a text file shown as binary (the `fixtures/**` truth and oracle files) with `--text -- <path>`.
- A batch is reviewed as one change by one council, so a defect in one commit can hold up the rest, and a revert undoes the whole batch. One commit per issue keeps a partial revert possible.
- A T1 change to a build or gate script, a lockfile or a toolchain pin can now merge without the admin. The council reviews every change, `verify` and main's post-merge run test it, and a revert is the way back, but nobody checks it by hand. The scripts that decide what `verify` runs (`build/verify-scope.mjs`, `build/gates.mjs`, `build/rust.mjs`) are the ones to watch.
- The skills stay T2, as the admin ruled that agent instruction files are. A first version of this record moved every skill except four to T1; the admin's ruling, relayed on 2026-11-10 after the PR that carried it was open, put `.claude/skills/**` back. The skills tell agents how to ship, and `babysit-pr/scripts/pr-wait`, which tags comments as trusted or untrusted, runs with the admin's `gh` login, so an agent steered by injected text could otherwise edit one in a T1 PR that the same repo's council reviews.
- The gate checks a verdict's hash, tier, rounds and open counts, and does not read its `phases`. The two-phase rule is therefore kept by the author running `council.mjs`, until the gate verifies that a verdict came from a real run (issue #79).
- Everything 0012 recorded about accepted risks applies only while a delegate is configured, which none is. The Gardener account itself is not touched by this change: the admin revokes its token and removes it as a collaborator on this repo and the sandbox repo, outside the repo, if they want it gone.
- To go back, restore the previous `tiers.t2Paths` from git history. To add a delegate again, record a new decision.
