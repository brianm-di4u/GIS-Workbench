# 0011: Post-merge retries infrastructure failures once

- **Date:** 2026-11-09
- **Class:** design
- **Issue:** none; the admin approved it in chat on 2026-11-09
- **Status:** accepted

## Context

Main went red twice on 2026-11-09 from GitHub, not from code. In #103 the binaryen download returned a 504. In #130, the `app`, `sidecar` and `verify` jobs of run 42670909876 never started, so `verify` read as abandoned. Each opened a main-red issue, which blocks every merge until the admin re-runs the run by hand.

## Decision

A post-merge run that failed only because of GitHub is re-run once, automatically. Nothing else is retried.

- **What counts as infrastructure.** `.pipeline/lib/classify-failure.mjs` reads the run's jobs and answers `infra` only when every failing leg (`app`, `sidecar`) failed before it ran any of our code: the job never started (missing, or no steps), or its only failed steps are setup steps (the job set-up and completion, post-run steps, checkout, setup-node, the app and sidecar setup actions, and the browser download). It lives under `.pipeline/` because it runs on main in jobs that hold tokens, and that path needs the admin's approval to change.
- **What is never retried.** A failed build, lint or test step is `real`, whatever else went wrong in the same run. So is any leg that was cancelled after it started, since a job timeout looks like that, and so is anything the classifier can't read or can't explain. When it is unsure, it says `real`. The flake rule is unchanged: a test failure is never retried, and a test that fails and then passes is still a finding.
- **Attempt 1 only.** The retry runs for a first attempt that failed. A second failure, of any kind, opens the main-red issue as before.
- **A separate workflow.** GitHub refuses to re-run a run that is still going, so a job inside `post-merge.yml` can't re-run its own run. `.github/workflows/post-merge-retry.yml` starts when a post-merge run completes, and calls `gh run rerun <run> --failed`. It runs only when the run failed, was a push, was on `main` and was attempt 1, and the one job that checks out code checks out the default branch, never the triggering head.
- **Permissions.** The new workflow's default is `{}`. Two jobs split the work so that no repository code runs with `actions: write`. `classify` has `actions: read` and `contents: read`, runs the classifier, and passes on only its `infra` or `real` answer as a job output. `retry` has `actions: write` and nothing else, checks out nothing and runs no repository script: it calls `gh run rerun` when the answer is `infra`. No job uses a third-party action. post-merge runs only on a push to main, so no PR code ever reaches `actions: write`. The agent token is unchanged and still can't dispatch workflows, which `release.yml` relies on. The `record` job in post-merge gains `actions: read` to list the run's jobs. A third job, `report`, has `issues: write` and `pull-requests: read` (what `record` already has), `contents: read`, and `actions: read` to list the failed run's jobs.
- **The main-red issue.** On attempt 1, `record` runs the same classifier and skips the issue only when the answer is `infra`, which it also reaches when `verify` never started. The re-run's `record` then reports as usual: it closes an open issue on green and opens one on red. Withholding a report on a prediction is only safe if something reports when the prediction fails, so `report` in the retry workflow opens the issue whenever no re-run happened: the failure was real, the retry workflow classified it differently, `gh run rerun` was refused, or the `classify` or `retry` job failed. It reports only when the `verify` job itself did not succeed (or its result can't be read), because a run can also go red when `record` or `delegates` fails while both legs passed, and that is not a red main. It is idempotent, and `monitor.mjs post-merge` takes `--run` and `--sha` so the issue names the failed run, not the retry's.

## Consequences

- An infrastructure failure on main costs one automatic re-run instead of a blocked main and a hand-run by the admin.
- A real failure costs nothing new: it opens the issue on attempt 1, as before.
- The classifier is wrong in one direction only by design: a real failure it calls `infra` gets one extra run, and then fails again and opens the issue on attempt 2. A setup step that fails for a real reason, such as a broken lockfile in `npm ci`, costs that one extra run too.
- A setup action is one step to GitHub, so a deterministic failure inside it, such as a bad lockfile in `npm ci` or a checksum mismatch on the binaryen download, is called `infra` and retried once. It then fails again and opens the issue on attempt 2. The cost is one extra run.
- `record` and the retry workflow each run the classifier, a few seconds apart, and read the same jobs list, so they agree unless GitHub's answer changes between the two reads. `report` covers that: the issue opens.
- Residual risk: the re-run joins post-merge's concurrency group, which keeps one pending run. A re-run can displace a newer pending run, or be cancelled behind newer work, and then attempt 2 never reports. The newer push has its own post-merge run, which reports main's state. A missing leg counts as never started because that is what #130 looked like (its jobs list held only `record`); a test fails if the legs the classifier names stop matching what `verify` waits for.
- The retry workflow can't report if it never gets a runner, which in an outage like #130 is possible. Then there is no re-run and no issue until the next push's run.
- It lands in two PRs, because the agents' token can't write workflow files: the classifier, its tests and this record first, then the two workflow changes, `monitor.mjs` and `docs/ROLLBACK.md`, which the admin pushes. The first PR changes nothing at run time. The second PR's tests check that the two workflows gate the same way; that `classify` has exactly `actions: read` and `contents: read`, `retry` has exactly `actions: write`, and the default is empty; that `retry` has no `uses:` and calls no repository file; that no third-party action is used; and that the classifier names the legs `verify` waits for.
- What was verified locally: the classifier's unit tests, those workflow checks, and a parse of both workflow files. actionlint was not installed and was not run. What only GitHub can show: that `gh run rerun --failed` is accepted from `workflow_run`, that the jobs API lists the steps by the names the classifier matches, and that the re-run's `record` closes the issue. The first real proof is the first infrastructure failure after this lands. Until then the step names in the classifier are a best reading of GitHub's output, and a name it doesn't recognise only makes it answer `real`, which is today's behaviour.
- To undo it, delete `post-merge-retry.yml`, the "Will this failure be retried?" step in `record`, and the classifier.
